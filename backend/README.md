# Backend runtime and safety notes

This document began as notes for the first isolated T2V backend slice. Vibe Director has since grown story, screenplay, production image, audio, video, Media Prep, shared-library, and assembly routes. Treat the code and [current phase review](../plans/progress_review.md) as authoritative when older details below conflict; the initial test counts and “not implemented” statements are historical, not current capability claims.

The API does **not** start ComfyUI workers at server startup. Generation actions are admitted only when the selected workflow, runtime/GPU guard, and explicitly enabled worker are ready. Keep live generation owner-clicked. Current local implementation and remaining acceptance gates are tracked in [the handoff](../plans/HANDOFF.md).

## API and storage

Start the HTTP adapter explicitly with `PYTHONPATH=. python -m story_builder.isolated_server` after setting `VIBE_DIRECTOR_DATA_DIR` to a product-owned data directory. Optional `VIBE_DIRECTOR_LEDGER_PATH` must remain inside that root; otherwise the database is `<data-dir>/storage/production/ledger.sqlite3`. Optional `VIBE_DIRECTOR_GRAPH_PATH` selects the exact graph file, which must match the pinned hash. Server binds only `127.0.0.1` (default port `3020`, override `VIBE_DIRECTOR_PORT`). It does not start any worker. Set `COMFYUI_ROOT`, `COMFYUI_URL`, and optionally `VIBE_DIRECTOR_COMFYUI_CONTAINER` / `VIBE_DIRECTOR_COMFYUI_CONTAINER_OUTPUT` when the ComfyUI container name or its output mount differs from defaults. GPU telemetry can be written elsewhere with `VIBE_DIRECTOR_GPU_TELEMETRY_PATH`. Set `VIBE_DIRECTOR_ENABLE_T2V=1` (legacy `STORY_BUILDER_ENABLE_H3_T2V=1` is also accepted) and optionally `VIBE_DIRECTOR_T2V_SMOKE_MANIFEST` (legacy `STORY_BUILDER_H3_T2V_SMOKE_MANIFEST` is also accepted) when the operator explicitly configures T2V. The ComfyUI container and ledger settings still accept their legacy Story Builder names as fallbacks for existing shared installations. Readiness is checked on `GET /api/status`, workflow-specific capability/catalog routes, or an explicit `POST /api/video/jobs`; server startup itself makes no runtime request.

F5 dataset preparation is a separate, explicit Media Prep action. If the API's default Python does not have the donor preparation dependencies, configure `AUDIO_TOOLS_PYTHON` **in the API server and worker environment before startup** to a Python with `soundfile` and `datasets`, for example `/path/to/preparation-env/bin/python`. The read-only preflight checks that interpreter, the local F5 source/vocabulary/checkpoint and `ffprobe`; a ready result enables preparation only, never training. The queued job copies selected, workspace-owned audio and exact transcripts into the product data directory and validates the dataset there. It does not install packages, load model weights, initialize CUDA, run the F5 training command or train a model. Do not use the example path literally; select a locally verified environment.

`GET /api/media/{workspace_id}/assets` lists shared workspace media with pagination and kind filters. `POST` to the same route accepts a bounded upload; `GET /api/media/{workspace_id}/assets/{asset_id}/content` serves validated bytes with range support. Media search, annotations, SEO ranking, analysis tools and generated-asset registration are implemented in the current product paths; see `plans/progress_review.md` for exact local evidence and the owner acceptance still outstanding. Do not use this older paragraph as a feature inventory.

## Initial T2V and image-worker implementation notes

The following sections document the original backend contracts and environment variables. They are not a current feature inventory; use the current phase review for implemented journeys and open acceptance gates.

`GET /api/images/workflows` explicitly checks the pinned API graphs, configured model files, live ComfyUI node classes and a successful smoke manifest for that exact workflow version. It does not submit a job. `POST /api/images/validations` compiles four candidate graphs for Assisted manual preview only. Fully automated correctly skips image generation. `GET /api/images/worker` reports the separate image worker heartbeat. `POST /api/images/jobs` persists an idempotent candidate batch only when workflow, GPU admission and the explicitly enabled worker are ready; `GET /api/images/batches/{batch_id}?workspace_id=...` reads its durable status. Character jobs may carry a current accepted screenplay revision and character graph record; the API validates both and saves their source, graph and screenplay IDs in durable job settings and generated-asset metadata. Character candidates can only be selected for the exact target they were generated for. `POST /api/images/jobs/{job_id}/accept` adds a compatible image role to a completed candidate in that same workspace; the candidate bytes remain in the shared media library. The job database is product-owned at `<data-dir>/storage/production/image-jobs.sqlite3` unless overridden by `VIBE_DIRECTOR_IMAGE_JOBS_DB`, which must remain under the data root for both API and worker.

The image worker is never started by the API. An operator must explicitly run `PYTHONPATH=. python -m story_builder.isolated_image_worker --enable-worker` with the same `VIBE_DIRECTOR_DATA_DIR`, `COMFYUI_ROOT`, `COMFYUI_URL`, and optional `VIBE_DIRECTOR_IMAGE_JOBS_DB`. The worker uses the serialized Comfy/GPU guard, watchdog and telemetry. Do not enable it until the selected workflow passes readiness and `/api/video/runtime` reports a safe GPU state. Jobs claimed before prompt reservation may be recovered after restart; ambiguous Comfy submits are held for reconciliation and never automatically resubmitted. Image workflow pages and shared-library reference staging have since been implemented. This file's original `501` and provisional-screen statements are obsolete; consult the current phase review and code before relying on them. No live GPU generation is implied by local tests.

To explicitly enable the durable consumer, run a separate terminal with the same `VIBE_DIRECTOR_DATA_DIR`, optional ledger/graph paths and runtime settings: `PYTHONPATH=. python -m story_builder.isolated_worker --enable-worker`. The alternative is `VIBE_DIRECTOR_ENABLE_WORKER=1` when invoking that module. Without this explicit opt-in the API capability reports `dispatch.available=false` and new job POSTs fail closed. The worker uses the existing `ProductionWorkerSupervisor`; it observes known prompt IDs after restart and never re-submits an uncertain prompt. It will leave queued jobs untouched while T2V or GPU readiness is unavailable, and checks readiness again in prepare. `GET /api/video/worker` exposes its local process heartbeat/status.

Routes:

- `POST /api/video/validations` with `{ "request": ... }` returns the normalized immutable request, canonical hash and predicted compile preview; it performs no readiness request or submit.
- `GET /api/video/capabilities` reuses the source T2V model/node/feature-flag/hash-verified smoke checks and adds the host GPU guard plus worker dispatch status. `GET /api/video/runtime` returns read-only temperature/clock status. Generation is blocked if telemetry is unavailable, temperature is at/above 90 C, or graphics clock is above 2100 MHz. The owner approved the 90 C application cutoff on 2026-10-21; the 2100 MHz ceiling and other safeguards remain; no clocks are changed.
- `POST /api/video/jobs` with workspace/clip/idempotency key/request (and for retakes `retake_of_job_id` plus `keep_original`) is an explicit Generate operation. It requires capability `available=true`, including a live worker consumer; otherwise it returns 503 without creating a ledger run/job.
- `GET /api/video/jobs/{job_id}`, `GET /api/video/jobs/{job_id}/events` and `GET /api/video/jobs/by-idempotency/{key}?workspace_id=...` are read-only. The idempotency lookup recovers a lost create response and never re-POSTs.
- `POST /api/video/retakes/{job_id}` with an explicit `{ "keep_original": true|false }` returns an editable saved-request draft and creates no job. A later Generate POST creates the retake. `POST /api/video/jobs/{job_id}/accept` accepts a reviewable output. “Discard” only marks a prior asset as a garbage-collection candidate after acceptance; this slice performs no deletion, and referenced assets are tracked separately.
- `GET /api/video/assets/{asset_id}` serves verified product-owned video bytes with HTTP range support for playback.

The adapter aliases `workspace_id` to the ledger's `project_id` and `clip_id` to `shot_id`; run configuration is `control_mode=manual`, `entry=isolated`, with Director gates disabled. It creates no screenplay, scene, or story canon. The full normalized request is stored in both the ledger snapshot and facade metadata. The same SQLite database holds isolated identity/idempotency/retake metadata and asset/reference records; it is not a second execution state machine. Retakes use independent takes with a metadata lineage link, never the ledger's predecessor-wait chain. `recovery_required` cannot be retaken until reconciliation resolves it.

Output collection is injected into the reused worker, downloads Comfy outputs into a temporary area using `media_jobs.collect_outputs`, requires native ffprobe video+audio streams, hashes and atomically stores valid media under `<data-dir>/assets/<workspace>/`, and returns stable content-derived asset IDs. Output paths are not returned to the browser. This collection code has not been exercised against a live Comfy output in this package.

## Boundaries and remaining work

Current CPU checks establish request validation, deterministic compilation, durable idempotent identity, service restart/concurrency behavior, atomic facade metadata, retake snapshot preservation, output retention metadata, API no-consumer/runtime gating and no-resubmit handling with injected fakes. They do not establish successful Comfy rendering, actual media collection/playback, recovery through a real backend restart, user-browser usability, or operator-safe GPU generation. Current real host snapshot reported by parent was 48 C / 2431 MHz; because this exceeds the preserved 2100 MHz ceiling, live T2V availability is currently blocked. Do not change GPU clocks. The independent watchdog retains its source behavior and only exists during an explicitly started real worker prompt.

### First manual R2V validation

The launcher enables `VIBE_DIRECTOR_ENABLE_T2V=1` and `VIBE_DIRECTOR_ENABLE_R2V=1` and starts the shared video worker. Manual admission checks the pinned graph, models, live node schemas, worker and GPU guard. A previous render is not required for the first owner-clicked test. Automated T2V still requires its verified smoke evidence. Automated R2V remains blocked until the manual worker collects a hash-verified video containing both video and audio streams; it records provenance at `<data-dir>/.vibe-director-r2v-smoke.json`. T2V/FL2VA evidence cannot satisfy this gate. Setting either enable flag to `0` disables admission for that workflow.
