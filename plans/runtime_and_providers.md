# Runtime supervision and provider choices

This note supplements `integration.md`, `automation.md`, `video_gen.md` and `ux_shared.md`. Those plans remain authoritative for product flow and run policy. FFLF/R2V/T2V are ComfyUI workflow choices; reasoning/model providers are a separate setting and do not select or alter a video workflow.

## Local generation and live acceptance

Before any authorized live generation, inspect the selected graph, required node/runtime versions and model files against the actual running ComfyUI installation; a stored graph or old smoke result alone does not establish readiness.

Reuse Story Builder `services/gpu_runtime.py`, `services/gpu_watchdog.py` and `services/media_jobs.py` admission/submission safeguards; do not replace their ownership checks. The runtime defines an 83°C cutoff and 2100 MHz ceiling, the independent watchdog monitors thermal state and telemetry through ComfyUI HTTP stalls, and media submission checks watchdog admission before POST. Relevant inspected-file SHA256: `gpu_runtime.py` `1afb61596068b4594c3f9c5e555ed2476b5955c22ebec98a59a7aa8a78524d32`, `gpu_watchdog.py` `f4f4ccfe5d148620456ca0d94f3903755867528a2980b843d9348d800c7ec7cc`, `media_jobs.py` `c76608d880d09f966e914ee283999f44d06905731332ebc7321cf0d9bb6a98e0`. Keep an independent monitor active while a browser task runs and through pause/reconnect/recovery. The 85°C maximum is recorded in the legacy release operator guidance, not the `gpu_runtime.py` cutoff. Treat 83°C/2100 MHz as existing code behavior and 85°C as legacy operator evidence until the hardware-specific policy is confirmed; never alter GPU clocks. Stop dispatch and follow existing safeguards if monitoring is lost or a limit is reached.

For a new generation adapter/workflow that lacks adequate retained evidence, prepare the complete prompt, settings, exact selected references, graph identity/readiness report, monitor and queue view first. Then ask the user to click **Generate**. Do not automate that click or dispatch work behind the scenes. Observe the exact durable job and monitor progress; verify the produced native media and full input snapshot; retain logs, hashes and review artifacts. This human gate applies to bounded acceptance tests and does not change Manual/Semi/Full behavior in a user-started, explicitly configured run. Choose the smallest representative real case for each uncovered adapter/workflow; existing accepted evidence should be reused instead of repeating an exhaustive legacy matrix.

Show any usable UI created or changed in the Codex browser using `open_in_codex`, reload it from the intended branch/backend, and confirm the correct version. Mark fixture data and mock outputs as mocks. Startup, page load, refresh and reconnect must never create a new submission or trigger test generation. Recovery reconciles the exact existing job; a worker may continue a previously user-authorized durable Manual/Semi/Full run under its saved policy and GPU safeguards, and must not repeat an ambiguous POST. Schedule bounded FFLF live acceptance in the final implementation stage. Keep it unavailable/unverified for live use until that acceptance demonstrates its exact current graph, inputs, output and recovery behavior; do not describe planned workflow support as proven runtime readiness.

## Reasoning/model providers

Keep reasoning-provider selection independent from GPU/video workflow selection. Codex CLI is the initial application completion and acceptance baseline: the integrated app must work end-to-end using the configured Codex engine/model before alternate providers or flexible model selection are considered. The inspected `services/reasoning_provider.py` already supports Codex and Ollama with configured defaults, but the current per-run context pins provider rather than model and `DEFAULT_CODEX_MODEL` is a configured default, not model discovery. Preserve `provider_exec_guard.py` and structured JSON parsing. Do not add OpenCode, direct GPT/compatible API adapters, a general model picker, or weaker Ollama/Qwen model support as current completion gates. Existing Ollama support may remain unchanged; it need not be removed or tested for this Codex-first acceptance. Shared prompts, schemas and optional skills can be reused later, but every future adapter/model still needs its own compatibility, context, tool, authentication and structured-output checks. One working Qwen model is not proof that every API-compatible model works. When alternatives are later approved, enumerate configured/discovered capabilities, pin both provider and model per run, and show a recovery choice rather than silently falling back.

For the Codex-first baseline, use its existing CLI authentication; do not demand an API key. Credential entry, custom base URLs and flexible model identifiers belong to later provider adapters and should be requested only if the chosen adapter needs them. Existing Story Builder settings do not store credentials, so secure credential storage is new work; never place raw keys in the current provider settings file. Keep credentials in a backend-managed secret store or secure secret reference. Never place raw keys in Git, logs, browser storage, prompt exports or durable job/request snapshots. Saving a credential is explicit; pin selected provider/model settings to the project or run so reconnects and retakes cannot silently change them. A provider health test may incur a small charge: state that before the user explicitly runs the check, and keep it separate from GPU generation.

Later multi-provider adapters/catalog, discovery, secure credential storage and compatible-API response handling are new integration work; do not assume they are copy/paste changes. The current Codex default behavior falls back to Codex for unsupported stored provider names; when a user-selectable catalog is introduced, use explicit unavailable/error recovery instead of silent fallback. Unknown compatibility, context limits, structured-output support or billing behavior stays labeled unverified until checked for that configured model. Development delegation is separate: the provider deferral changes app completion scope, not the established Luna coding delegation.

## Remaining product decisions and scope

Final assembly, soundtrack/mixing, transitions and export remain in later issue #14 until the user defines the journey. FFLF acceptance is scheduled for the final implementation stage and remains unavailable until demonstrated. OpenCode/direct API/flexible model selection and weaker-model support are explicitly deferred until the complete application works with Codex. Provider-specific secret storage and policy for remote data submission require explicit later design. No provider credential, model, UI or runtime is asserted ready by this plan.
